# 版本记录规范

这份文档定义 CHun 在 `vx.y.z` 下的记录方式。

目标不是做严格的语义化版本承诺，而是给个人开发过程留下一份可回看的演进轨迹。

## 基本格式

- 版本格式：`vX.Y.Z`
- 记录时间：默认使用该版本 tag 指向 commit 的提交时间
- 记录对象：`X`、`Y`、`Z` 全部记录，不省略小版本

## 各字段含义

### `X` 变更

`X` 表示阶段性里程碑。

适合出现在这些情况：

- 框架主形态变化
- 核心子系统正式落地
- 对外推荐用法发生明显变化
- 项目进入新的开发阶段

例子：

- `v0.x.x -> v1.x.x`
- 从脚本工具集合进入统一 session / registry / transport 架构

### `Y` 变更

`Y` 表示一个明确的新能力块，或同一阶段内的重要功能推进。

适合出现在这些情况：

- 新增一个可独立描述的能力模块
- 现有模块出现明显扩展
- 维护者会把它看作“这次确实做成了一件事”

例子：

- 新增 `replay`
- 新增 `workflow`
- 新增 `cache-backed lazy loading`

### `Z` 变更

`Z` 表示在当前大能力方向下继续打磨。

通常包括：

- bug 修复
- 结构收口
- 语法糖补齐
- 文档补齐
- 小范围重构

虽然 `Z` 的定位偏“小”，但在 CHun 的开发文档里仍然要单独记录，因为这也是演进轨迹的一部分。

## 建议写法

每个版本建议至少包含：

- 版本号
- 日期
- 一句话主题
- 这次主要做了什么
- 如果需要，可补一行“意义”

建议格式：

```md
## v1.2.1 - 2026-04-20

主题：重构 fmt 写入算法内核并接入 pwntools backend

- 完成了什么
- 调整了什么
- 修复了什么

意义：

- 为什么这个版本值得被记住
```

## 时间来源

版本文档中的日期默认取自：

- tag 指向 commit 的 `commit date`

如果后续需要保留“打 tag 的时间”而不是“commit 时间”，可以另加字段；当前阶段先统一使用 commit 提交时间，保持简单。

## 当前维护约定

- 每个本地正式 tag 都应写入版本历史
- `backup-*` 之类备份 tag 不写入正式版本历史
- 可以在版本历史里保留一句原始 tag 主题，再补充维护者视角的解释
